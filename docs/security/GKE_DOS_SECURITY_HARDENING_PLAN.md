# Philobiblus GKE DoS and application security hardening plan

## 1. Purpose

This plan hardens the public Philobiblus API deployed on GKE Autopilot against accidental overload, credential abuse, HTTP floods, common web attacks, lateral Pod traffic, and unbounded infrastructure cost.

The plan is written for the current architecture:

- project: `grace-enhanced`;
- cluster: `philobiblus-dev-gke` in `asia-southeast1`;
- global external managed GKE Gateway;
- GitHub Pages frontend;
- FastAPI backend behind `Service/philobiblus-backend`;
- Redis catalogue cache;
- private Cloud SQL PostgreSQL through Cloud SQL Auth Proxy sidecars;
- Managed Service for Prometheus and Cloud Monitoring;
- Terraform Google provider `~> 8.2` and Kubernetes/Helm providers.

This work reduces risk; it cannot guarantee that every denial-of-service attack will be stopped. Google provides automatic network-level protection for supported external load balancers, while Layer 7 protection still requires an attached Cloud Armor policy and application controls.

## 2. Current findings

### 2.1 Public routing is broader than intended

`kubernetes/helm/philobiblus/templates/gateway.yaml` currently routes `PathPrefix /` to the backend. Consequently, these backend paths can be reached through the public Gateway:

- `/api/**`;
- `/metrics`;
- `/docs`;
- `/redoc`;
- `/openapi.json`;
- `/health`;
- `/`.

The comment in `backend/app/main.py` that `/metrics` is reachable only through ClusterIP is therefore not currently true.

### 2.2 No edge Layer 7 security policy is attached

There is no `google_compute_security_policy`, `GCPBackendPolicy`, Cloud Armor rate limit, or WAF rule in the current Terraform and Helm configuration.

### 2.3 Expensive endpoints have no abuse controls

- `/api/auth/login` performs password hash verification.
- `/api/auth/register` hashes a password and writes to PostgreSQL.
- `/api/uploads/cover` accepts an image of up to 10 MiB and can wait 30 seconds for ImgBB.
- recommendation and catalogue endpoints can perform database or ML service work.
- HPA and ResourceQuota limit the blast radius but do not reject malicious requests before they consume backend resources.

### 2.4 Pod traffic is unrestricted

The Helm chart currently has no Kubernetes `NetworkPolicy`. Redis is a ClusterIP and is not public, but every Pod that can reach the namespace can attempt to connect to it.

### 2.5 Existing controls that must be preserved

- HTTPS and Google-managed certificate;
- private GKE nodes;
- Workload Identity Federation;
- Secret Manager synchronization;
- non-root containers with dropped Linux capabilities;
- HPA maximum of six backend Pods;
- namespace ResourceQuota and LimitRange;
- database connection pool limit;
- private Cloud SQL connectivity;
- Prometheus scraping through `PodMonitoring`.

## 3. Target traffic flow

```text
Internet
   |
Google Front End: automatic network DDoS protection
   |
Cloud Armor: host validation, WAF, path-specific rate limiting
   |
GKE Gateway: HTTPS and only PathPrefix /api
   |
Service/philobiblus-backend
   |
FastAPI: user/account/global Redis-backed limits and concurrency bounds
   |
Backend Pods ---- Redis
   |                 |
Cloud SQL Proxy      NetworkPolicy: backend only
   |
Private Cloud SQL
```

Operational endpoints remain internal:

```text
GKE health checker ----> /health
Managed Prometheus ----> /metrics
kubectl port-forward ---> /docs, /openapi.json, /health, /metrics
```

## 4. Principles and rollout rules

1. Apply route minimization before enforcement.
2. Create Cloud Armor in `gke-platform` before Helm references it from `gke-app`.
3. Run every Cloud Armor WAF and rate-limit rule in preview first.
4. Enable load balancer request logging while preview rules are evaluated.
5. Never enable default-deny egress until all required destinations have been measured and allowlisted.
6. Apply one security layer at a time and run a smoke test after each layer.
7. Preserve an explicit rollback path for every phase.
8. Do not expose a NodePort, LoadBalancer Service, Pod IP, Cloud Run URL, `/metrics`, or `/health` as a workaround.
9. Do not use CORS as an access-control or DoS control. Non-browser clients ignore CORS.
10. Do not log JWTs, passwords, Secret Manager values, request bodies, or ImgBB keys.

## 5. Phase 0: capture baseline and produce a threat model

### Files to add

- `docs/security/GKE_DOS_SECURITY_BASELINE.md`
- `docs/security/GKE_DOS_INCIDENT_RUNBOOK.md`

### Baseline evidence

Record without secrets:

- Git SHA and immutable image digests;
- Gateway, HTTPRoute, HealthCheckPolicy, Service and endpoint status;
- current external paths and response codes;
- current GCP backend service name generated by Gateway;
- HPA min/max/current replicas;
- request rate, p95, 5xx ratio and Cloud SQL connections under normal traffic;
- current GKE Dataplane V2 status;
- current Cloud Armor and load balancer logging status;
- current monthly budget alerts and project quotas.

### Threats in scope

| Threat | Primary control | Secondary control |
|---|---|---|
| Volumetric L3/L4 attack | Google Front End protection | Cloud Armor telemetry |
| HTTP request flood | Cloud Armor rate limiting | application limiter and HPA ceiling |
| Distributed L7 flood | Cloud Armor WAF/rules | optional Adaptive Protection and global circuit breaker |
| Credential stuffing | login rate limit | account/IP limiter and audit alert |
| Registration spam | registration rate limit | optional CAPTCHA/email verification |
| Expensive upload abuse | upload rate limit | size, concurrency and timeout limits |
| SQLi/XSS/scanner traffic | Cloud Armor CRS 4.22 WAF | ORM validation and application tests |
| Pod lateral movement | NetworkPolicy | service accounts and least-privilege IAM |
| Cost exhaustion | HPA/ResourceQuota/quotas | budget and traffic alerts |

## 6. Phase 1: minimize the public attack surface

### 6.1 Route only `/api`

Modify `kubernetes/helm/philobiblus/templates/gateway.yaml` so the backend `HTTPRoute` uses:

```yaml
matches:
  - path:
      type: PathPrefix
      value: /api
```

Keep the dedicated HTTP-to-HTTPS redirect route. The redirect may match the host broadly, but only `/api` must have an HTTPS backend route.

Expected external behavior:

| Path | Expected result |
|---|---|
| `/api/books/public` | normal application response |
| `/api/auth/login` | normal application response |
| `/metrics` | load balancer/Gateway 404 |
| `/docs` | load balancer/Gateway 404 |
| `/redoc` | load balancer/Gateway 404 |
| `/openapi.json` | load balancer/Gateway 404 |
| `/health` | load balancer/Gateway 404 |
| `/` | load balancer/Gateway 404 |

This routing change must not modify the existing `HealthCheckPolicy`. GKE Gateway health checks call the backend service using the configured `/health` path independently of the public HTTPRoute. The health endpoint must continue to return HTTP 200 without authentication.

### 6.2 Disable API documentation in the deployed environment

Modify `backend/app/main.py` and the Helm values to introduce `ENABLE_API_DOCS`:

- local/test default: enabled;
- GKE default: disabled;
- when disabled, set `docs_url=None`, `redoc_url=None`, and `openapi_url=None`;
- never use the frontend origin or CORS settings to decide whether docs are enabled.

The docs can still be enabled temporarily in an isolated environment. Production debugging should prefer tests, logs, and `kubectl port-forward` rather than publishing Swagger.

### 6.3 Tighten CORS without treating it as DoS protection

Replace wildcard methods and headers with the methods and headers actually used by the frontend:

- methods: `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`;
- headers: `Authorization`, `Content-Type`, and any explicitly verified application header;
- origin: exact GitHub Pages HTTPS origin only;
- keep credentials only if required by the frontend behavior.

### Phase 1 acceptance criteria

- all frontend journeys continue to work;
- external operational paths return 404;
- `/health` still marks the backend healthy;
- Managed Prometheus still scrapes `/metrics` directly from Pods;
- the Gateway and HTTPRoute report accepted/resolved conditions;
- no direct public Service or Pod endpoint has been introduced.

## 7. Phase 2: create Cloud Armor with Terraform

### 7.1 Terraform ownership

Create the policy in `infrastructure/terraform/gke-platform` because it is edge/platform infrastructure and must exist before the application Helm release.

Planned files:

- modify `gke-platform/main.tf` or add `gke-platform/cloud-armor.tf`;
- modify `gke-platform/variables.tf`;
- modify `gke-platform/outputs.tf`;
- modify `gke-platform/terraform.tfvars.example`;
- update the relevant Terraform documentation.

Add variables with validation rather than hard-coded project values:

```text
enable_cloud_armor
cloud_armor_waf_rules_preview
cloud_armor_sensitive_rate_limit_preview
cloud_armor_general_rate_limit_preview
cloud_armor_api_host
cloud_armor_login_count
cloud_armor_login_interval_seconds
cloud_armor_register_count
cloud_armor_register_interval_seconds
cloud_armor_upload_count
cloud_armor_upload_interval_seconds
cloud_armor_general_count
cloud_armor_general_interval_seconds
```

Output only the non-sensitive policy name:

```text
cloud_armor_security_policy_name
```

### 7.2 Security policy rule order

Cloud Armor evaluates rules by ascending priority and applies the highest-priority matching enforced rule. WAF rules must therefore precede rate-limit rules. Preview matches continue evaluation and do not block traffic.

Proposed policy order:

| Priority | Match | Initial action |
|---:|---|---|
| 100 | CRS 4.22 SQL injection, sensitivity 1 | deny 403, preview |
| 110 | CRS 4.22 XSS, sensitivity 1 | deny 403, preview |
| 120 | CRS 4.22 local file inclusion, sensitivity 1 | deny 403, preview |
| 130 | CRS 4.22 remote file inclusion, sensitivity 1 | deny 403, preview |
| 140 | CRS 4.22 remote code execution, sensitivity 1 | deny 403, preview |
| 150 | CRS 4.22 scanner detection, sensitivity 1 | deny 403, preview |
| 900 | wrong host for the configured API domain | deny 404, preview |
| 1000 | exact `/api/auth/login` path | throttle by IP, preview |
| 1010 | exact `/api/auth/register` path | throttle by IP, preview |
| 1020 | exact `/api/uploads/cover` path | throttle by IP, preview |
| 1030 | recommendation paths | throttle by IP, preview |
| 2000 | paths beginning `/api/` | general throttle by IP, preview |
| 2147483647 | all remaining traffic | allow during preview rollout |

Use current CRS 4.22 stable rule names, for example:

```text
evaluatePreconfiguredWaf('sqli-v422-stable', {'sensitivity': 1})
evaluatePreconfiguredWaf('xss-v422-stable', {'sensitivity': 1})
```

Do not use the default sensitivity of 4 for the first rollout because it has a higher false-positive risk.

### 7.3 Initial preview thresholds

These thresholds are observation defaults, not final production limits:

| Endpoint group | Preview threshold/key |
|---|---:|
| Login | 20 requests per 300 seconds per IP |
| Register | 10 requests per 600 seconds per IP |
| Upload | 10 requests per 600 seconds per IP |
| Recommendations | 60 requests per 60 seconds per IP |
| All `/api/` paths | 300 requests per 60 seconds per IP |

Start with `throttle`, `conform_action=allow`, and `exceed_action=deny(429)`. A throttle rule can later be changed to a rate-based ban; a rate-based ban cannot be changed back to throttle in place. Enforce-on-key must be IP for the first version.

After at least 24 hours of representative traffic and a controlled load test, tune the general threshold toward the measured safe capacity. Shared NAT addresses must be considered before lowering per-IP limits.

### 7.4 Request parsing and logs

Configure Cloud Armor JSON parsing for the JSON API if supported by the pinned provider schema. Configure WAF inspection up to the required supported limit, recognizing that Cloud Armor WAF inspection is not a replacement for upload size limits.

Verbose WAF logging may include request snippets and personal data. Use it only during short tuning windows. Keep normal access logging enabled.

## 8. Phase 3: attach Cloud Armor through one GCPBackendPolicy

GKE permits only one `GCPBackendPolicy` per target Service. Combine the security policy, access logging, backend timeout, and later backend settings in a single resource.

### Files

- `kubernetes/helm/philobiblus/templates/backend-policy.yaml`;
- `kubernetes/helm/philobiblus/values.yaml`;
- `infrastructure/terraform/gke-app/main.tf`;
- optionally `infrastructure/terraform/gke-app/variables.tf` when an explicit override is needed;
- `scripts/gcp-gke/30-app-apply.sh` Helm lint inputs.

### Intended manifest

```yaml
apiVersion: networking.gke.io/v1
kind: GCPBackendPolicy
metadata:
  name: philobiblus-backend
spec:
  default:
    securityPolicy: <platform remote-state output>
    timeoutSec: 30
    logging:
      enabled: true
      sampleRate: 1000000
  targetRef:
    group: ""
    kind: Service
    name: philobiblus-backend
```

`sampleRate: 1000000` means 100% during preview analysis. Reduce it after tuning if log cost becomes excessive. Do not shorten the backend timeout below the upload provider timeout until uploads are moved to a separate Service/route or redesigned asynchronously.

The GKE application module should read `cloud_armor_security_policy_name` from platform remote state and pass it to Helm. Terraform dependency remains directional:

```text
gke-platform: Cloud Armor policy
        ↓ remote-state output
gke-app: Helm GCPBackendPolicy
```

### Attachment checks

- `GCPBackendPolicy` exists in the same namespace as `Service/philobiblus-backend`;
- status condition `Attached=True`;
- no older conflicting `GCPBackendPolicy` targets the Service;
- Cloud Armor policy appears on the Google backend service generated by Gateway;
- load balancer logs contain `previewSecurityPolicy` fields when test traffic matches a preview rule.

## 9. Phase 4: analyze preview data, then enforce safely

### Observation window

Use at least 24 hours of normal traffic plus controlled tests for:

- login success and failure;
- registration;
- book search containing punctuation and common SQL-like words;
- review/comment input containing markup-like text;
- upload filenames and multipart bodies;
- admin operations;
- catalogue load tests;
- intentional harmless WAF probes in the project's own endpoint.

### Logs to inspect

- `previewSecurityPolicy.name` and priority;
- `previewSecurityPolicy.configuredAction`;
- `previewSecurityPolicy.preconfiguredExprIds`;
- `previewSecurityPolicy.rateLimitAction.outcome`;
- enforced policy outcome;
- HTTP status, latency and path;
- source distribution without copying IP values into the report.

### Promotion gates

A rule may move from preview to enforced only when:

- its intended malicious/over-limit tests match;
- representative valid frontend traffic does not match;
- false positives are documented and tuned by rule ID/path where necessary;
- rollback has been tested;
- alerting is active;
- the policy has been stable for the agreed observation window.

Promote rules separately in this order:

1. wrong-host rule;
2. login/register/upload rate limits;
3. general API rate limit;
4. high-confidence CRS sensitivity-1 stable WAF rules;
5. optional rate-based bans after throttle behavior is understood.

Keep canary WAF rules in preview at a higher priority before later promoting stable rule updates.

## 10. Phase 5: add a Redis-backed application limiter

Cloud Armor protects the edge primarily by client properties such as IP. The application must additionally enforce account and authenticated-user fairness.

### Design

Implement an atomic Redis token bucket or sliding-window limiter. Do not use read-then-write Redis operations without a transaction/Lua script because concurrent Pods would exceed the intended limit.

Suggested namespaces:

```text
philobiblus:ratelimit:login:<ip-hash>:<username-hash>
philobiblus:ratelimit:register:<ip-hash>
philobiblus:ratelimit:user:<user-id>:<route-group>
philobiblus:ratelimit:upload:<user-id>
philobiblus:ratelimit:global:<route-group>
```

Do not store plaintext email, username, JWT or full IP in Redis keys. Use an HMAC or keyed hash where identity data is needed.

### Application limits to start in tests

| Scope | Candidate limit |
|---|---:|
| Failed login by account and IP | 5 per 5 minutes |
| Register by IP | 3 per 10 minutes |
| Upload by authenticated user | 3 per 10 minutes |
| Recommendation by user | 30 per minute |
| Authenticated writes by user | 60 per minute |
| Anonymous catalogue by IP | 60 per minute |

Return HTTP 429 with a bounded integer `Retry-After` header. Add Prometheus counters for allowed, rejected, Redis-error, and fallback decisions. Route labels must use templates/groups, never usernames or IDs.

### Global overload circuit breaker

Do not hard-code a global RPS threshold before rerunning the cache/pool capacity test. Derive it from the highest passing steady-state RPS:

```text
steady global admission rate = floor(highest passing RPS * 0.80)
temporary burst capacity = steady rate * 2
```

Using the old 23.4 RPS result only as an example gives approximately 18 admitted RPS with a burst of 36. Recalculate from the post-cache benchmark before enforcement.

### Redis failure behavior

- catalogue reads may fail open and query PostgreSQL;
- ordinary read limits may use a bounded per-Pod fallback limiter;
- login, registration and upload must not become unlimited;
- expensive endpoints should use fail-closed or a conservative local fallback;
- Redis outage must emit a metric and alert;
- local fallback limits must account for the six-Pod maximum.

## 11. Phase 6: upload and server resource controls

The current 10 MiB check happens after multipart traffic has reached FastAPI. Add layered controls:

1. Reject missing or excessive `Content-Length` for the upload route when compatible with browser multipart requests.
2. Keep the application byte-count limit as the authoritative fallback.
3. Validate image signatures/magic bytes, not only `Content-Type`.
4. Set a lower outbound ImgBB timeout where tests permit.
5. Bound concurrent upload operations per Pod and globally.
6. Never decode an image into memory merely to validate it without pixel/dimension limits.
7. Add Uvicorn keep-alive and concurrency limits only after benchmark validation; rejected overload should return quickly rather than queue for 60 seconds.

If Gateway-wide body/timeout settings would harm ordinary APIs, split upload traffic into a separate Kubernetes Service and HTTPRoute before applying upload-specific limits.

## 12. Phase 7: Kubernetes NetworkPolicy

### 12.1 Verify enforcement first

Confirm GKE Dataplane V2/network policy enforcement before creating policies. A manifest without an enforcing network plugin provides no isolation.

### 12.2 Roll out ingress isolation before egress isolation

Planned Helm template:

```text
kubernetes/helm/philobiblus/templates/network-policies.yaml
```

Add feature flags under `networkPolicy` in `values.yaml`:

```text
enabled
defaultDenyIngress
defaultDenyEgress
allowExternalGatewayToBackend
allowManagedPrometheus
```

Ingress rollout order:

1. Redis: permit TCP 6379 only from backend Pods.
2. Recommendation: permit TCP 8080 only from backend Pods and approved test Jobs.
3. Backend: permit TCP 8000 from the GKE Gateway/load-balancer path, Managed Prometheus collectors, and labelled load-test Jobs.
4. Seed Job: no ingress.
5. Add namespace default-deny ingress only after the component policies render correctly.

For Dataplane V2, validate the documented `ipBlock` behavior before using `0.0.0.0/0` to represent external Gateway traffic; Pod traffic is treated differently from external IP-block traffic. Confirm with connectivity tests rather than assumptions about rewritten source addresses.

Modify the k6 load-test Job to carry an explicit component label so it can be allowed without opening backend ingress to arbitrary Pods.

### 12.3 Egress policy inventory

Do not enable default-deny egress until policies allow all required traffic:

| Source | Destination | Purpose |
|---|---|---|
| all relevant Pods | cluster DNS TCP/UDP 53 | service discovery |
| Workload Identity Pods | `169.254.169.254/32` ports 80/8080 on Dataplane V2 | GKE metadata server |
| backend | Redis TCP 6379 | cache and rate limiting |
| backend | recommendation TCP 8080 | ML recommendations |
| backend | ImgBB HTTPS 443 | cover uploads |
| Cloud SQL proxy sidecar | private Cloud SQL address TCP 5432 | database |
| model fetcher | Google Cloud APIs/Storage HTTPS 443 | retrieve model artifact |
| seed | Cloud SQL through its sidecar | seed data |

The private Cloud SQL range must come from Terraform outputs/data rather than a hard-coded address. Broad HTTPS egress should be documented as residual risk if domain-aware filtering is unavailable at Kubernetes L3/L4.

### NetworkPolicy acceptance criteria

- frontend API works through Gateway;
- probes remain healthy;
- Prometheus targets remain up;
- backend reaches Redis, recommendation, ImgBB and Cloud SQL;
- recommendation and Redis reject connections from an unlabelled test Pod;
- Workload Identity and Secret Manager synchronization continue to work;
- DNS works;
- the k6 capacity script remains usable with its approved label;
- network-policy drops are observable where supported.

## 13. Phase 8: monitoring, alerts and incident response

### Load balancer and Cloud Armor logging

Enable 100% access logging during preview. After enforcement and tuning, choose a sustainable sample rate while retaining enough data for rate-limit analysis. Cloud Armor decisions are recorded in load balancer logs only when backend service logging is enabled.

Do not leave verbose WAF request-body logging enabled continuously because request fragments can contain personal data.

### Alerts to add to `gke-observability`

| Alert | Initial condition |
|---|---|
| Cloud Armor enforced deny spike | sustained deny count/rate above baseline |
| Cloud Armor preview match spike | sustained preview matches |
| Rate-limit exceed | repeated `RATE_LIMIT_THRESHOLD_EXCEED` |
| Failed login spike | application metric above baseline |
| Application limiter rejects | sustained 429 increase |
| Backend 5xx | ratio above 2% for 5 minutes |
| Backend p95 | above 1 second for 5 minutes |
| Backend HPA ceiling | desired replicas equals 6 while latency/errors rise |
| Cloud SQL connections | approach measured safe/database limit |
| Redis errors | any sustained limiter/cache Redis error |
| Redis unavailable | no Ready replica or scrape target |
| Cost anomaly/budget | configured GCP budget thresholds |

Each alert must link to `docs/security/GKE_DOS_INCIDENT_RUNBOOK.md` and include immediate diagnosis steps.

### Incident runbook actions

The runbook must cover:

1. verify whether traffic is malicious or a legitimate spike;
2. identify matching Cloud Armor rule/path without publishing client data;
3. lower or enforce an existing preview threshold through reviewed Terraform;
4. temporarily block a confirmed source only with an expiry and evidence;
5. protect login/upload first if database or workers are saturated;
6. preserve logs and test artifacts;
7. rollback false-positive rules;
8. review cost and Cloud SQL impact after the incident.

Avoid manual console-only policy changes except during an active incident. Any emergency change must be imported or represented in Terraform afterward to remove drift.

## 14. Phase 9: testing strategy

### Static validation

- backend unit tests;
- rate limiter concurrency tests;
- Helm lint with every security feature enabled;
- Helm render inspection;
- Terraform formatting and validation;
- Terraform plans for `gke-platform`, `gke-app`, and `gke-observability`;
- secret scan before commit.

### Functional tests

1. Public `/api` GET succeeds.
2. Authentication and admin routes remain functional.
3. External operational paths return 404.
4. Internal `/health` and `/metrics` succeed.
5. A harmless SQLi/XSS test appears in preview logs and is not blocked during preview.
6. Rate-limit test appears as preview exceed.
7. After enforcement, excess requests receive 429 while conforming traffic succeeds.
8. Redis limiter returns `Retry-After` and remains atomic across multiple backend Pods.
9. Redis outage follows the designed fallback behavior.
10. NetworkPolicy connectivity matrix passes.

### Capacity and resilience tests

- repeat the established VU tiers with identical workload parameters;
- verify that rejected excess requests return quickly;
- ensure accepted traffic remains below p95 and error thresholds;
- observe HPA readiness timing;
- confirm Cloud SQL does not exhaust connections;
- confirm Cloud Armor reject traffic does not reach backend request counters;
- test rollout and Pod termination while traffic is active;
- compare costs/log volume before and after access logging changes.

Do not use third-party targets or uncontrolled traffic. Run all security/load tests only against the owned Philobiblus endpoint.

## 15. Deployment sequence

The executing agent must use this order:

1. Capture Phase 0 evidence.
2. Implement and deploy `/api`-only routing and disabled production docs.
3. Verify health checks and monitoring.
4. Create Cloud Armor preview policy through `gke-platform` Terraform.
5. Add and apply the single `GCPBackendPolicy` through `gke-app`.
6. Confirm attachment and request logging.
7. Collect preview traffic and tune false positives.
8. Enforce route-specific throttles one by one.
9. Enforce stable sensitivity-1 WAF rules one by one.
10. Deploy the application-level Redis limiter.
11. Run functional and capacity tests.
12. Apply ingress NetworkPolicies and validate.
13. Inventory egress, then optionally apply egress NetworkPolicies.
14. Add alerts and finish the incident runbook.
15. Publish a final security validation report containing evidence and remaining risks.

## 16. Rollback plan

### Route rollback

Restore the prior HTTPRoute only if frontend API routes were accidentally omitted. Do not restore `/` merely to expose health or metrics; repair the dedicated internal configuration instead.

### Cloud Armor rollback

1. Change the offending enforced rule back to preview through Terraform.
2. Apply `gke-platform`.
3. Confirm accepted traffic and policy logs.
4. Detach the policy through Helm only if the entire policy attachment is defective.

Do not delete the policy before removing the `GCPBackendPolicy` reference.

### Application limiter rollback

Disable the limiter through a controlled configuration flag and redeploy the previous immutable image digest. Preserve metrics/logs explaining the rollback.

### NetworkPolicy rollback

Disable the specific restrictive policy through Helm values. Do not delete unrelated namespace resources or the complete cluster.

## 17. Completion criteria

The hardening project is complete only when:

- only `/api` is publicly routed;
- public `/metrics`, `/docs`, `/openapi.json`, `/health`, and `/` return 404;
- GKE health checks and Managed Prometheus remain healthy;
- Cloud Armor is Terraform-managed and attached with `Attached=True`;
- rate limits and selected WAF rules have completed preview and controlled enforcement;
- valid frontend traffic has no unexplained Cloud Armor false positive;
- application limits protect login, registration, upload and recommendation;
- excess requests return 429 promptly;
- Redis failure behavior is tested;
- ingress NetworkPolicies isolate backend dependencies;
- alerts and incident runbook are active;
- post-hardening capacity remains within accepted latency/error thresholds;
- Terraform state and live resources have no unexplained drift;
- the final report states residual risks, Cloud Armor tier, logging sample rate, and tested capacity.

## 18. Explicit residual risks

- Per-IP limits can affect users behind shared NAT and can be bypassed by distributed clients.
- Cloud Armor Standard rate limits and WAF do not provide every Enterprise/Adaptive Protection capability.
- Kubernetes NetworkPolicy is L3/L4 and cannot filter domains or HTTP paths.
- A single Redis Pod remains an availability dependency for shared cache/rate state, although designed fallback limits impact.
- Broad HTTPS egress for ImgBB or Cloud Storage may remain necessary without an egress proxy.
- Budget alerts notify; they do not automatically stop attacks or spending.
- Application vulnerabilities still require dependency scanning, patching, authorization tests, secret rotation and secure code review.
