\reportchapter{IV. Mô tả phần mềm cài đặt (nếu có)}
\reportsectionplain{a. Không cần mô tả cách cài đặt các ứng dụng phụ}
Người dùng truy cập Philobiblus bằng trình duyệt và không phải cài phần mềm desktop. GKE, Helm, Terraform, Cloud SQL và các dịch vụ quan sát chỉ phục vụ triển khai, vận hành.

\reportsectionplain{b. Mô tả ngắn gọn cách cài đặt phần mềm được phát triển}
Phiên bản được mô tả trong báo cáo chạy trên GKE Autopilot. Frontend tĩnh gọi API qua Gateway; backend và recommendation chạy trong namespace philobiblus, Redis cung cấp cache, còn dữ liệu nghiệp vụ nằm trên Cloud SQL.

\reportsectionplain{Quy trình triển khai trên GKE}
Hạ tầng được tách thành các Terraform state gke-platform, gke-app, gke-mlops và gke-observability. gke-platform quản lý GKE Autopilot, mạng, Gateway và Cloud Armor; gke-app quản lý namespace, Workload Identity, Cloud SQL, Helm release và cấu hình ứng dụng; gke-mlops quản lý bucket versioned, IAM theo prefix, MLflow và pipeline retrain; gke-observability quản lý Cloud Monitoring dashboard cùng alert policy. Tách state riêng giúp việc thay đổi dashboard hoặc model pipeline mà không lập kế hoạch lại toàn bộ cluster.

Image được tham chiếu bằng digest bất biến để cùng một release luôn trỏ tới cùng nội dung. Helm tạo Deployment, Service, Redis, HTTPRoute, GCPBackendPolicy, NetworkPolicy, PodMonitoring, readiness/liveness probe và HPA. Backend dùng tối thiểu 2, tối đa 6 Pod trong đợt đo tải; probe chỉ đưa Pod vào Service khi sẵn sàng. Workload nhận quyền Google Cloud qua Workload Identity, trong khi secret được cung cấp ngoài chart thay vì ghi trực tiếp trong repository.

Release đi qua kiểm thử, build image, lấy digest, validate Terraform, render Helm và chờ rollout. Metric nội bộ được PodMonitoring thu vào Google Managed Service for Prometheus; Cloud Monitoring và Cloud Logging là giao diện quan sát của GKE.

\reportsectionplain{Quan sát hệ thống và xử lý sự cố}
FastAPI xuất /metrics trong mạng nội bộ. PodMonitoring thu request rate, latency, mã phản hồi, rate limit và cache operation; Cloud Monitoring kết hợp chúng với CPU, memory, restart và số replica. Log stdout/stderr được Cloud Logging thu theo cluster, namespace và container.

\reportsectionplain{Chuỗi kiểm soát DevSecOps}
CI sử dụng Gitleaks, Semgrep, pip-audit, npm audit và Trivy; bước phát hành tạo SBOM và ký image bằng Cosign trước khi triển khai. Cảnh báo quét được phân loại theo khả năng khai thác thay vì xử lý như nhau.

Sau khi workload hoạt động, Cloud Armor, Gateway, NetworkPolicy, securityContext và Redis rate limiter bảo vệ các ranh giới khác nhau. HTTPRoute chỉ công khai /api; /metrics, /docs, /openapi.json và /health trả 404 qua Gateway nhưng vẫn dùng được cho probe và thu metric nội bộ. Request thử SQL injection và XSS khớp rule CRS 4.22 của Cloud Armor ở chế độ preview. Chuỗi đăng nhập sai vượt ngưỡng bị rate limiter ứng dụng trả 429, cho thấy lớp bảo vệ trong backend vẫn hoạt động khi rule biên chưa chuyển sang Enforce.
